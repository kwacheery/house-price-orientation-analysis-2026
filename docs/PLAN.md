## 0. 一页摘要

**一句话**：用多平台二手房数据预测房源单价，并在控制面积、区域、楼层、房龄等因素后，量化“朝向”对房价的溢价。

- **主任务（建模得分点）**：房价回归预测，目标变量优先用**单价（元/㎡）**，避免总价被面积主导。
- **分析主线（项目特色）**：朝向溢价——朝南、南北通透相对朝北，在同等条件下贵多少，溢价是否存在区域差异。
- **工程链路**：采集 → 原始落盘 → 清洗 → 特征工程 → 建模 → Web 可视化，一条命令可复现。
- **数据规模**：3 人组，每人 ≥1000 条，全组 ≥3000 条；**主分析城市广州**，链家/贝壳多城市首页样本用于跨城市稳健性检验。W1 已采集 3326 条（房天下 1274、链家 1032、贝壳 1020）。
- **Web 双形态**：本地 FastAPI 动态版（答辩主用）+ GitHub Pages 静态版（在线预览/备份）。
- **核心产出**：可运行代码、清洗前后对比、模型指标与消融实验、朝向溢价置信区间、Web 页面、10–15 页报告。

**这个项目不是**“各朝向均价柱状图”。朝向只是特征之一，主模型仍是完整房价预测；否则会踩大纲“只做描述性统计 −15 分”的红线。

## 1. 选题与问题定义

### 1.1 背景

购房者在看房时普遍关心朝向与采光，开发商和中介也常以“南北通透”“全南户型”作为卖点。但朝向到底值多少钱，不能直接比较各朝向的平均单价——朝南的房子往往同时位于更好的小区、更好的楼层、更大的面积。需要把其他因素控制住，才能估计朝向的边际影响。

### 1.2 研究问题

| 编号 | 问题 | 对应产出 |
|---|---|---|
| Q1 | 在控制面积、房龄、楼层、区域/小区后，不同朝向的单价差异是否显著？ | 回归系数、置信区间、假设检验 |
| Q2 | 朝向溢价在不同区县/板块是否一致？ | 分区县/板块溢价表、热力图 |
| Q3 | 把朝向加入房价预测模型，能带来多少增量价值？ | 消融实验：ΔR²、ΔRMSE |
| Q4 | 哪类房源对朝向更敏感（低总价/高总价、老房/新房）？ | 分组误差分析与交互特征 |

### 1.3 分析边界

1. **观察性数据，不做因果断言**。报告统一表述为“控制其他变量后相关”“溢价估计”，不写“朝南导致涨价”。
2. **零结果也如实报告**。如果控制变量后朝向不显著，就报告“未发现显著溢价”及置信区间，不调参凑显著、不 p-hacking。
3. **不采集隐私**。不采房东/经纪人姓名、电话、微信、身份证、门牌号；不绕过登录、验证码、付费墙。
4. **只做课程学习用途**，数据不商用、不再分发。

## 4. 数据源与采集

### 4.1 站点选择

无账号、以“哪家好爬用哪家”为原则，按优先级排序。3 人各认领一个主站点，组内不重复。

| 优先级 | 站点 | 广州入口 | 定位 | 采集方式 | 难度 | 主要字段 |
|---:|---|---|---|---|---|---|
| 1 | 链家 | `gz.lianjia.com` | 主站点，静态列表页 | Requests + bs4 | 低 | 标题、户型、面积、朝向、楼层、建成年份、总价、单价、区域、小区 |
| 2 | 房天下 | `gz.esf.fang.com` | 第二站点，城市子域名结构统一 | Requests + bs4 | 低–中 | 房源名称、介绍、售价、小区、单价 |
| 3 | 贝壳 | `gz.ke.com` | 第三站点，样本补充 | Playwright 或页面内 JSON 接口 | 中 | 小区、总价、面积、单价、位置、更新时间 |
| 4 | 安居客 | `guangzhou.anjuke.com` | 备选，反爬较强 | Requests + bs4，注意反爬 | 中高 | 房源名称、售价、小区、地址、单价 |

**W1 实测结论（2026-11-10，详见本节 4.7）**：

- 链家、贝壳、房多多 robots 为 `User-agent: *` → `Disallow: /`；中原 robots 明确禁止自动化访问。
- 链家/贝壳仅**城市首页**可稳定访问（31 条/页）；第 2 页、区县页、筛选页会触发登录或人机验证。
- 房天下广州列表页可正常翻页（60 条/页），字段完整率高；安居客、58 同城在连续请求后触发安全验证。
- 最终执行分工：**A 房天下广州（深度） + B 链家多城市首页 + C 贝壳多城市首页**；广州仍为主分析城市。

**站点选择规则**：

1. W1 每站试爬 20 页，按“成功率、字段完整率、速度、是否触发验证码”打分。
2. 3 人各选一个得分最高的不同站点，不重复；不预设“必须用某一家”。
3. 某站中途被封或字段不可用，顺延到下一优先级站点，并记录切换原因。
4. 报告中写清“人—站点—区县—数据量”对应关系，作为分工与采集评分的依据。

### 4.2 城市与区县

- **主城市：广州**。房源量大、区县多、朝向样本充足，适合按区县拆分翻页，也便于做“朝向×区域”溢价对比。
- **多城市对照**：链家、贝壳各取 33–34 个城市首页样本（每城约 31 条），用于“朝向溢价是否跨城市稳定”的稳健性检验；主模型、主溢价表仍以广州数据为准，不把多城市样本混入主结论。
- **覆盖区县**：天河、越秀、海珠、荔湾、白云、黄埔、番禺、花都、南沙、从化、增城；按房源量分配采集配额。
- **数据量**：3 人 × ≥1000 条，全组 ≥3000 条；先保证主城区（天河、越秀、海珠、荔湾、白云、黄埔），再补外围区。
- **备选**：若广州全量采集后仍不足 3000 条，第三位成员可改用佛山/深圳作为“不同城市”分工；不默认启用。
- 单城市不丢分：大纲要求“每人至少负责一个不同网站或不同城市”，本项目用“3 个不同站点”满足。

### 4.4 采集策略

1. **先试点再全量**：每站先爬 20 页，确认列表页字段、翻页规则、反爬强度；试点通过后才开全量。
2. **列表页为主**：列表页已包含面积、朝向、楼层、建成年份、总价、单价、小区，优先保证覆盖率。
3. **详情页为辅**：对缺失字段（电梯、装修、挂牌时间）按需补采，控制请求量；不做全量详情页。
4. **翻页**：按广州 11 个区县拆分查询条件，规避单条件约 100 页上限；每个区县独立翻页、独立断点。
5. **断点续爬**：每页落盘 JSONL，记录 `city/source/district/page`；失败重试 3 次，保留失败队列。
6. **限速**：请求间隔 1–3 秒随机；单站点并发不超过 2；夜间不跑大批量。
7. **异常识别**：连续空页、验证码页、登录跳转、状态码 403/429 时停止并告警，不绕过。
8. **原始数据不可变**：`data/raw/{source}/{city}/{date}.jsonl` 只追加不修改；清洗从 raw 重新生成。

### 4.7 W1 站点筛查记录（v0.3）

筛查日期 2026-11-10，每站 1–3 页，无账号、不破解验证码。结论如下：

| 站点 | robots 结论 | 实测可访问性 | 最终用途 |
|---|---|---|---|
| 链家 | `User-agent: *` → `Disallow: /` | 城市首页 31 条；`pg2`/区县/筛选页 → 登录或人机验证 | **B：多城市首页** |
| 贝壳 | 同链家，`Disallow: /` | 同上 | **C：多城市首页** |
| 房天下 | 部分目录禁止，列表页路径允许 | 广州、深圳正常翻页，60 条/页 | **A：广州区县翻页** |
| 安居客 | `User-agent: *` → `Allow: /` | 手机端首页可用；连续请求后触发安全验证 | 不作为主站点，冷却后可补采 |
| 58 同城 | 允许，但 `Disallow: /*?*` | PC 第 2 页验证码；手机端 `/p2/` 仍返回第 1 页 | 不作为主站点 |
| 中原（广州） | 开头明确“禁止未经许可的自动化访问” | 可访问但不采 | 放弃 |
| 乐有家 | 允许 `/esf/` | 第 2 页强制登录 | 备选 |
| 赶集 | 允许 | 房源频道已下线（404） | 放弃 |
| 百姓网 | 无法获取 | 跳转公众号拦截页 | 放弃 |
| 房多多 | `Disallow: /` | — | 放弃 |
| 我爱我家 | — | 无广州站 | 放弃 |
| 佛山/东莞/珠海/中山 房天下 | — | 521 拦截 | 放弃 |

**执行规则**：

1. 链家/贝壳每个城市只取首页 31 条；不请求 `pg2`、区县页、筛选页，不破解验证码。
2. 准备 ≥40 个候选城市，取成功 33–34 城 × 约 31 条 ≈ 1000 条/人；失败城市跳过并记录原因。
3. 房天下广州按 11 区县翻页，优先主城区；每区县独立断点，单区县页数上限可配。
4. 任一站点出现验证码/登录跳转，立即停止该站点并记录，不重试绕过。
5. 字段口径统一到 4.3 数据字典；链家/贝壳列表页缺失的建成年份、装修、电梯设“未知”，不做无依据填充。
6. **合规披露**：链家/贝壳 robots 明确禁止抓取。本项目经组内确认，仅在课程学习范围内做低频、限量、非商用采集；不采集个人隐私、不再分发原始数据，报告第 2 章如实说明该限制与替代方案。

**关键结论与限制**：

## 6. 预处理方案（20 分核心）

### 6.1 处理流程

```
raw JSONL
  → 字段标准化 / 类型转换
  → 去重
  → 缺失值处理
  → 异常值检测与处理
  → 文本与朝向标准化
  → 清洗后数据 clean.csv
  → 特征工程 features.csv
```

每一步输出计数：输入行数、删除行数、修改行数、输出行数，汇总为 `reports/preprocessing_summary.csv`。

### 6.2 去重

- **完全重复**：所有字段一致，保留一条。
- **业务重复**：`小区 + 面积 + 户型 + 总价 + 朝向 + 楼层` 一致，视为同一房源重复挂牌，保留最新 `crawl_time`。
- **跨平台重复**：同一小区、面积差 ≤1㎡、户型一致、总价差 ≤2%，标记 `cross_source_dup`，建模时只保留主站点一条，避免重复样本导致指标虚高。
- 输出去重日志：重复组数、保留规则、影响行数。

### 6.3 类型转换

| 原始值 | 转换后 | 规则 |
|---|---|---|
| `120万` / `120.5万` | `120.0` | 去“万”，转 float |
| `13408元/㎡` | `13408` | 去单位，转 float |
| `89.5㎡` | `89.5` | 去单位 |
| `中楼层/共18层` | `floor_level=中`, `total_floors=18`, `floor_ratio=0.5` | 正则拆分；低/中/高映射为区间中值比例 |
| `2010年建` | `2010` | 去“年建” |
| `南 北` | `["南","北"]` | 空格/斜杠/逗号拆分 |

单价校验：`abs(unit_price - total_price*10000/area) / unit_price > 5%` 标记为疑似单位错误，人工抽查后处理。

### 6.4 缺失值处理

| 字段 | 缺失策略 | 依据 |
|---|---|---|
| `unit_price` | 若总价与面积齐全则重算；否则删除 | 目标变量不可缺 |
| `area` | 删除 | 核心特征，无法可靠填补 |
| `orientation_raw` | 设“未知”类，不删；缺失率 >40% 时启动预案 | 朝向是分析主线，删除会引入选择偏差 |
| `build_year` | 设“未知”并加 `age_missing` 标记；或用同小区中位数填充并标记 | 房龄重要但可容缺 |
| `floor_raw` | 设“未知”类 | 楼层与朝向可能相关，不能随意填 |
| `decoration` | 设“未知”类 | 类别特征 |
| `elevator` | 设“未知”类 | 类别特征 |
| `community` | 保留“未知小区”，不参与小区固定效应 | 高基数 |

**原则**：优先保留样本 + 显式“未知”类别 + 敏感性分析；禁止无依据 `dropna()` 或 `fillna(0)`。

### 6.5 异常值检测

- **单价**：按区县计算 IQR（广州 11 区；样本 <50 的区县回退到全市 IQR），剔除 `[Q1−1.5IQR, Q3+1.5IQR]` 之外；同时用 3σ 做对照，报告中说明为何选 IQR（房价右偏、非正态）。
- **面积**：<10㎡ 或 >1000㎡ 视为异常；别墅/整栋需人工确认后保留并标记。
- **总价**：<10 万或 >1 亿视为疑似单位错误，人工抽查。
- **建成年份**：早于 1950 或晚于采集年份视为异常。
- **楼层**：`floor_level` 超出 `total_floors` 视为异常。
- **处理方式**：优先修正（单位错误）→ 无法修正则删除 → 保留但标记（极端但真实的高价房），并做“剔除 vs 保留”敏感性对比。
- 输出：异常值数量表、处理前后箱线图、剔除前后模型指标对比。

### 6.6 文本与朝向标准化

| 原始值示例 | 标准化结果 | 说明 |
|---|---|---|
| `南` | 主朝向=南；`is_south=1` | 单朝向 |
| `南北` / `南 北` | 主朝向=南；`is_south_north=1`；方向数=2 | 南北通透 |
| `东南` | 主朝向=东南 | 8 方位之一 |
| `西南` | 主朝向=西南 | 8 方位之一 |
| `东西` | 主朝向=东；方向数=2 | 多朝向，主朝向按“南>东>西>北”优先级 |
| `暂无数据` / 空 | 主朝向=未知；`orientation_missing=1` | 不删样本 |

- 统一 8 方位：东、南、西、北、东南、西南、东北、西北 + 未知。
- 文本清洗：去 HTML 标签、首尾空白、全角转半角、去不可见字符。
- 标题仅用于探索性分析，不直接进模型，避免文本噪声与过拟合。

### 6.7 标准化

- 线性/Ridge 模型：数值特征 Z-Score；类别特征 One-Hot。
- 树模型：不强制标准化，但统一放进 Pipeline，保证预处理一致。
- **只在训练集 fit**，测试集 transform，防止数据泄漏。
- 报告中说明：房价右偏，线性模型对目标做 `log1p`，评估时反变换回元/㎡。

### 6.8 预处理产物

- `data/processed/clean.csv`
- `reports/preprocessing_summary.csv`（每步行数变化）
- `reports/figures/missing_before_after.png`
- `reports/figures/outlier_boxplot.png`
- `reports/preprocessing_report.md`（策略、依据、前后对比）
- Web 页面复用同一份汇总 JSON，保证截图与系统一致。

## 7. 特征工程（20 分核心）

### 7.1 朝向特征（项目特色）

| 特征 | 类型 | 定义 | 业务含义 |
|---|---|---|---|
| `orientation` | 类别 | 主朝向 8 类 + 未知 | 基础类别特征 |
| `is_south` | 0/1 | 主朝向=南 | 朝南 |
| `is_south_north` | 0/1 | 同时含南、北 | 南北通透 |
| `orientation_count` | int | 朝向包含的方向数 | 采光面数量 |
| `orientation_score` | ordinal | 南 4、东南/西南 3、东/西 2、东北/西北 1、北 0 | 辅助排序特征，报告中说明为主观规则 |
| `orientation_missing` | 0/1 | 朝向缺失 | 缺失模式特征 |
| `south_ratio` | float | 朝南方向数 / 总方向数 | 朝南程度 |

> `orientation_score` 只作为辅助特征，主分析仍用 One-Hot + 回归系数，避免主观打分误导结论。

### 7.2 其他衍生特征

| 特征 | 定义 | 对应大纲示例 |
|---|---|---|
| `age` | 采集年份 − 建成年份 | 房龄 |
| `price_area_ratio` | 总价 / 面积（与单价互为校验） | 单价/总价比值 |
| `district_price_gap` | 房源单价 − 所在区县训练集均价，再除以区县均价 | 区域均价偏离度 |
| `floor_ratio` | 所在楼层 / 总层数 | 楼层位置 |
| `rooms` / `halls` | 从户型解析 | 户型结构 |
| `area_bin` | 面积分箱（<60、60–90、90–120、120–144、>144） | 面积段 |
| `decoration_level` | 毛坯 0、简装 1、精装 2、豪装 3、未知 −1 | 有序编码 |
| `has_elevator` | 有/无/未知 | 居住品质 |

### 7.3 编码方案

| 特征 | 编码 | 理由 |
|---|---|---|
| `orientation` | One-Hot（8+未知） | 类别少，可解释 |
| `district` | One-Hot（广州 11 区）+ 频次编码 | 区县少，可解释 |
| `community` | 频次编码；建模时可选 Target Encoding（OOF + 平滑） | 高基数，避免爆炸 |
| `decoration` | 有序编码 | 存在天然顺序 |
| `floor_level` | 有序编码 + `floor_ratio` | 保留顺序信息 |
| `city` | 主模型不使用（单城市常量）；仅启用备选城市时 One-Hot | 单城市无方差 |

**高基数处理**：小区名称不能直接 One-Hot。优先频次编码；使用 Target Encoding 时必须**折外（OOF）计算 + 平滑**，并在报告中说明防泄漏措施。

### 7.4 交叉特征（加分项）

- `朝向 × 楼层`：南向低楼层 vs 南向高楼层。
- `朝向 × 房龄`：老房朝南是否更稀缺。
- `房龄 × 区域`：老城区 vs 新城区。
- 交互项仅在树模型/线性模型中对比效果，避免盲目堆特征。

### 7.5 防泄漏清单

- [ ] 标准化只在训练集 fit。
- [ ] Target Encoding 用 OOF，禁止全量计算。
- [ ] `district_price_gap` 只用训练集统计量。
- [ ] 去重后再切分，防止同房源跨集合。
- [ ] 切分时按 `community` 做 Group Split 作为稳健性检验。
- [ ] 不把 `unit_price` 的任何直接变形（如总价/面积）重复放入特征造成目标泄漏。

### 7.6 特征字典与选择

- 输出 `docs/feature_dictionary.md`：特征名、定义、类型、缺失处理、来源。
- 用 permutation importance + 相关性矩阵做初步筛选；对高相关特征（|r|>0.9）保留业务解释性更强的一个。
- 特征选择结果写入报告，说明“为什么保留/删除”。

## 8. 建模与评估（20 分核心）

### 8.1 目标变量

- **主目标**：`unit_price`（元/㎡）。
- 线性模型对目标做 `log1p`，评估时反变换，指标仍在元/㎡ 尺度报告。
- 可选副目标：`total_price`（总价），用于对比“面积主导”的影响，不强制。

### 8.2 数据切分

- 主评估：80% 训练 / 20% 测试，固定随机种子（如 42），按 `district` 分层。
- 稳健性：`GroupShuffleSplit` 按 `community` 分组，检验“对未见小区”的泛化能力。
- 交叉验证：5 折；分组实验用 `GroupKFold`。
- 所有切分索引落盘，保证复现。

### 8.3 基线模型（必须做）

1. **全局均值**：所有房源预测同一单价。
2. **区域均值**：用所在区县训练集均价预测。
3. **面积单变量线性回归**：仅用面积。

主模型必须显著优于“区域均值”基线，否则模型没有业务价值。

### 8.4 候选模型

| 模型 | 作用 | 备注 |
|---|---|---|
| Ridge / 线性回归 | 可解释基线，输出朝向系数 | 必须做 |
| RandomForest | 非线性基线 | 必须做 |
| HistGradientBoosting | 主力模型，训练快 | 推荐 |
| XGBoost / LightGBM | 加分项，对比优势 | 可选 |

统一用 `Pipeline` 封装预处理 + 模型；超参数用 `GridSearchCV`/`RandomizedSearchCV`，禁止在测试集上调参。

### 8.5 评估指标

- MSE、RMSE、MAE、R²。
- 训练/测试指标同时报告，附 5 折均值 ± 标准差。
- 分区县、分价格段、分朝向分组的误差分析。
- 残差图、真实值 vs 预测值散点图。

### 8.6 朝向溢价分析（项目核心）

**模型**：

```
log(unit_price) = β0
                + Σ β_k · orientation_k
                + β1 · log(area)
                + β2 · age
                + β3 · floor_ratio
                + β4 · decoration_level
                + 区域固定效应 / 小区固定效应
                + 城市固定效应（多城市稳健性检验时）
                + ε
```

- 以“北”或“未知”为参照组（报告中说明选择）。
- 系数换算溢价：`premium = exp(β_k) − 1`，输出百分比与 95% 置信区间。
- **同小区比较**：加小区固定效应，或做“同小区 + 同户型 + 面积相近”的匹配样本对比，控制地段与楼栋差异。
- **统计检验**：Kruskal-Wallis 检验各朝向单价分布差异；必要时 Dunn 事后检验（校正多重比较）。
- **Bootstrap**：对溢价估计做 1000 次重采样，给出置信区间。
- **异质性**：分区县/板块/价格段重复估计，观察溢价是否稳定。
- **跨城市复现**：用链家/贝壳多城市首页样本重复估计，加入城市固定效应；只报告“方向/显著性是否一致”，不与广州主表混算。
- **结论纪律**：如果 CI 跨 0，写“未发现显著差异”，不强行解释。

### 8.7 消融实验（直接回答 Q3）

| 实验 | 特征集 | 指标 |
|---|---|---|
| A | 不含任何朝向特征 | RMSE / R² |
| B | 含朝向 One-Hot + 二值特征 | RMSE / R² |
| C | B + 朝向交叉特征 | RMSE / R² |

报告 `ΔR²`、`ΔRMSE` 和 permutation importance 排名。即使提升很小，也是诚实且有价值的结论。

### 8.8 误差分析

- 按区县、板块、价格段、朝向分组计算 RMSE。
- 找出高误差样本，分析原因（豪宅、别墅、异常面积、信息缺失）。
- 检查是否存在系统性偏差（如老房低估、豪宅低估）。

### 8.10 W4/W5 建模与溢价结果（2026-11-17）

脚本：`python -m models.train` → `python -m models.evaluate` → `python -m models.premium`。

| 模型（测试集，元/㎡） | RMSE | MAE | R² |
|---|---:|---:|---:|
| 全局均值基线 | 27425 | 19882 | −0.096 |
| 区县均值基线 | 19019 | 12017 | 0.473 |
| 面积单变量基线 | 25483 | 17727 | 0.053 |
| Ridge | 16779 | 10505 | 0.590 |
| RandomForest | 14216 | 8723 | 0.705 |
| **HistGradientBoosting（最优）** | **14106** | **8834** | **0.710** |

- R² 0.710 ≥0.65；相对区县均值基线 RMSE 降 25.8% ≥15%，两项验收达标。超参只在训练集 5 折 CV 搜索。
- **朝向溢价**：参照组“北”，控制 log(area)、floor_ratio、rooms、区县固定效应，HC3 稳健标准误；朝南 +4.1%（95% CI [−5.4%, +14.4%]，p=0.413），1000 次 bootstrap 结论一致 → 未发现显著溢价。原始分布的 Kruskal-Wallis 显著（p=2.5e−7），说明未调整差异来自混杂变量。
- **消融**（Ridge）：A 无朝向 R²=0.5953 / B 含朝向 0.5936 / C 加交叉 0.5937；朝向未带来预测增益（ΔR²=−0.0017），如实报告。
- **敏感性**：剔别墅/异常值后 Ridge RMSE 16698 → 12862；主口径保留全部样本并标记。
- **跨城市**：链家/贝壳 + 城市固定效应下朝南 −1.3%（p=0.80），方向与广州不一致且不显著，仅作稳健性参考，不混入主结论。
- **局限**：房龄/装修主样本全缺，无法作为控制变量；多重比较未做 FDR 校正；小区固定效应未纳入，详见 `reports/modeling_report.md`。

## 9. Web 可视化（15 分）

### 9.1 双形态架构

| 形态 | 运行方式 | 数据来源 | 预测方式 | 用途 |
|---|---|---|---|---|
| **本地版（主）** | FastAPI + 静态前端 | `/api/*` 实时读取数据库/处理后数据 | 后端加载完整模型 | 答辩、评分、现场演示 |
| **Pages 版（备）** | GitHub Pages 纯静态 | 预导出的 JSON | 导出 Ridge 系数，浏览器 JS 计算 | 在线预览、仓库链接、备份 |

- 两套共用同一份 `web/frontend/`，全部使用**相对路径**，保证本地与 Pages 子路径都能打开。
- 本地版是评分依据，满足大纲“前端调用后端接口”；Pages 版明确标注“静态演示”，不冒充动态后端。
- GitHub Pages 不能运行 Python，因此**不部署 FastAPI**；不写假接口，静态版直接读 JSON。

### 9.2 技术选型

- **后端**：FastAPI，提供数据与预测接口，同时托管静态前端。
- **前端**：原生 HTML/CSS/JS + ECharts（CDN 或本地文件），**不做 Node 构建**，降低现场演示与 Pages 部署风险。
- **本地启动**：`uvicorn web.backend.app:app --reload`，或统一入口 `python scripts/run_web.py`。
- **静态导出**：`python scripts/export_static.py` 生成 Pages 所需 JSON。
- **Pages 部署**：`.github/workflows/pages.yml`，推送到 `main` 后自动发布 `web/frontend/`。
- 备选：Flask + Jinja2 + ECharts；不引入 Vue/React，除非后续明确需要。

### 9.3 静态导出方案

```bash
python scripts/export_static.py
```

- 读取 `data/processed/` 与 `models/artifacts/`，输出：
  - `web/frontend/data/overview.json`
  - `web/frontend/data/preprocessing.json`
  - `web/frontend/data/orientation.json`
  - `web/frontend/data/metrics.json`
  - `web/frontend/data/importance.json`
  - `web/frontend/data/static_model.json`（Ridge 系数 + 编码映射）
- 聚合后的 JSON 体积控制在 1MB 以内，**提交到仓库**；Pages 构建不依赖原始数据和 Python 环境。
- 静态版预测用导出的 Ridge 模型（可解释、易在 JS 复现），页面标注“静态演示模型”；完整 GBDT 预测在本地版。
- 导出脚本与本地 API 共用同一份指标/图表计算函数，避免两套数字不一致。

### 9.4 页面结构

| 页面/区块 | 内容 | 本地版 | Pages 版 | 对应评分点 |

| 价格预测 | 输入区县/面积/朝向/楼层/房龄 → 返回预测单价 | POST API | JS Ridge | 交互 5 分 |

## 13. 风险与预案

| 风险 | 概率 | 影响 | 触发条件 | 预案 |
|---|---|---|---|---|
| 朝向缺失率过高 | 中 | 高 | 试点缺失 >40% | 改为“朝向+楼层+房龄”居住品质组合；或换站点/区县 |
| 朝向类别样本不足 | 中 | 中 | 主要朝向 <100 条 | 长尾合并为“其他”；只对样本充足类别做检验 |
| 三站中某站不可用 | 中 | 高 | 连续 403/验证码/字段缺失 | 按优先级顺延到下一站点；同城换区县；保证 3 人各有一个可用站点 |
| 反爬导致采集中断 | 中 | 高 | 403/429/验证码 | 降频、换时段、换站点；不绕过验证码 |
| 链家/贝壳翻页被验证码拦截 | 高 | 高 | `pg2`/区县/筛选页跳登录或人机验证 | 只取各城市首页；用多城市凑量；不破解验证码 |
| 多城市首页样本代表性不足 | 中 | 中 | 每城仅 31 条、默认排序 | 仅用于跨城市稳健性检验，不并入广州主结论；报告写明抽样偏差 |
| 链家区县字段缺失 | 高 | 中 | 城市首页卡片不展示区县，原始完整率 12.9% | W2 用小区/板块映射补全并标记来源；主分析用房天下区县数据 |
| 第三站点再次不可用 | 中 | 高 | 验证码/登录范围扩大 | 回退房天下广州 + 深圳；第三人转做预处理/Web，保留两站数据 |
| 同小区样本太少 | 中 | 中 | 同小区同户型配对 <30 组 | 用区县固定效应替代；报告中说明局限 |
| 模型 R² 不达预期 | 中 | 中 | R² <0.65 | 补特征（房龄/楼层/装修）、换模型；以“优于基线”为主目标 |
| 数据泄漏导致指标虚高 | 中 | 高 | 随机切分远高于分组切分 | 以分组切分为稳健性标准；检查 Target Encoding |
| Python 3.14 依赖不兼容 | 中 | 中 | pip 安装失败或导入报错 | W0 切换到 Python 3.12 venv 或 conda，不硬扛 |
| GitHub Pages 无后端 | 高 | 低 | 静态版无法运行 FastAPI | 静态 JSON + Ridge JS 预测，明确标注“静态演示”；本地版为主 |
| 时间不足 | 低 | 高 | W5 未冻结数据 | 砍加分项，保预处理 + 建模 + Web 主链路 |
| 现场演示故障 | 低 | 高 | 网络/环境异常 | 本地缓存数据、离线依赖、演示前完整彩排 |

## 14. 分工（3 人）

| 成员 | 主责站点 | 主责模块 | 交叉/备份 | W1 条数 | 答辩范围 |
|---|---|---|---|---:|---|
| A | 房天下广州（深度，区县翻页） | 采集框架、房天下解析、清洗/预处理 | 协助特征工程、模型评估 | 1274 | 房天下代码 + 预处理 |
| B | 链家多城市首页 | 特征工程、建模、朝向溢价分析 | 协助 Web、数据 QA | 1032 | 链家代码 + 模型 |
| C | 贝壳多城市首页 | Web 本地版 + Pages 静态版、报告整合、多城市复现 | 协助清洗、图表制作 | 1020 | 贝壳代码 + Web |

- 每人至少负责一个**不同站点**，满足大纲“不同网站或不同城市”的分工要求。
- 预处理、建模、可视化由三人共同参与：主责人写主代码，其他人至少完成一次代码 review、一组图表或一次复现。
- 报告分工表写清“人—站点—区县—数据量—模块—代码路径”，答辩时能现场打开对应代码。
- 若某站点不可用，按 4.1 优先级顺延，主责人不变，记录切换原因。
